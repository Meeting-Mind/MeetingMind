# Functional Requirements Detail

Google Sheets 기능요건(FR) 시트의 전체 우선순위(P0/P1/P2) 상세 기준 로컬 스냅샷이다.
각 항목은 원본 Sheet의 인수 기준, 관련 모듈/데이터, 상세 동작, 조건/권한, 실패/예외, 검증 기준을 보존한다.

## ① 공통 — 인증 / 인가

### FR-AUTH-01 회원가입(이메일)

- 우선순위: `P0`
- 요구사항: 이메일/비밀번호로 회원가입할 수 있어야 한다
- 인수 기준: 유효 이메일·비밀번호 입력 시 계정 생성 / 중복 이메일 거부
- 관련 모듈/데이터: User, AuthIdentity
- 상세 동작: 이메일, 비밀번호, 약관 동의 값을 받아 신규 User와 AuthIdentity를 생성한다.
- 조건/권한: 이메일은 유일해야 하며 비밀번호 정책을 통과해야 한다.
- 실패/예외: 중복 이메일은 409, 형식/정책 오류는 400으로 처리한다.
- 검증 기준: 정상 입력 시 계정이 생성되고 동일 이메일 재가입은 차단된다.

### FR-AUTH-02 이메일 형식·중복 검증

- 우선순위: `P0`
- 요구사항: 가입 이메일의 형식과 중복 여부를 검증해야 한다
- 인수 기준: 형식 오류·중복 시 고정 에러코드 반환
- 관련 모듈/데이터: /auth/signup
- 상세 동작: 가입 요청 시 이메일 형식과 기존 계정 존재 여부를 서버에서 검증한다.
- 조건/권한: 검증은 클라이언트 표시와 별개로 서버에서 반드시 수행한다.
- 실패/예외: 잘못된 형식은 400, 중복은 409와 고정 에러코드를 반환한다.
- 검증 기준: 오류별 고정 코드가 반환되고 계정은 생성되지 않는다.

### FR-AUTH-03 비밀번호 정책

- 우선순위: `P1`
- 요구사항: 비밀번호 복잡도 정책을 적용해야 한다
- 인수 기준: 최소 길이·문자조합 미충족 시 거부
- 관련 모듈/데이터: -
- 상세 동작: 비밀번호 최소 길이, 문자 조합, 금지 패턴을 검증한다.
- 조건/권한: 정책값은 운영 설정으로 관리하고 가입/변경/재설정에 동일 적용한다.
- 실패/예외: 정책 미충족 시 저장하지 않고 400을 반환한다.
- 검증 기준: 정책 미충족 케이스별로 가입과 변경이 모두 거부된다.

### FR-AUTH-04 소셜 로그인

- 우선순위: `P0`
- 요구사항: Google OAuth로 로그인할 수 있어야 한다
- 인수 기준: ID token 검증 성공 시 로그인/가입
- 관련 모듈/데이터: /auth/google
- 상세 동작: Google ID token을 서버에서 검증한 뒤 내부 세션을 발급한다.
- 조건/권한: issuer, audience, expiry, signature 검증을 통과해야 한다.
- 실패/예외: 검증 실패, 만료, audience 불일치는 401로 처리한다.
- 검증 기준: 유효 토큰만 로그인되고 잘못된 토큰은 계정 생성 없이 거부된다.

### FR-AUTH-05 소셜 계정 연결/생성

- 우선순위: `P1`
- 요구사항: 최초 소셜 로그인 시 계정을 생성 또는 기존 계정과 연결한다
- 인수 기준: 동일 이메일 계정 연결 규칙 적용
- 관련 모듈/데이터: AuthIdentity
- 상세 동작: 소셜 로그인 이메일과 기존 계정 이메일을 기준으로 연결 또는 신규 생성을 수행한다.
- 조건/권한: 동일 이메일 계정 병합 규칙이 확정되어야 한다.
- 실패/예외: 충돌/미확정 병합 케이스는 안전하게 연결을 보류한다.
- 검증 기준: 동일 이메일 시 의도한 규칙대로 AuthIdentity가 연결된다.

### FR-AUTH-06 로그인

- 우선순위: `P0`
- 요구사항: 이메일/비밀번호로 로그인할 수 있어야 한다
- 인수 기준: 자격 일치 시 토큰 발급 / 불일치 401
- 관련 모듈/데이터: /auth/login
- 상세 동작: 이메일/비밀번호를 검증하고 access/refresh 토큰을 발급한다.
- 조건/권한: 탈퇴/잠금 계정은 로그인 대상에서 제외한다.
- 실패/예외: 자격 불일치, 미가입, 탈퇴 계정은 401로 동일 처리한다.
- 검증 기준: 정상 계정은 토큰을 받고 실패 사유는 과도하게 노출되지 않는다.

### FR-AUTH-07 토큰 발급

- 우선순위: `P0`
- 요구사항: 로그인 시 access/refresh 토큰 쌍을 발급한다
- 인수 기준: 만료시간 포함 토큰 쌍 반환
- 관련 모듈/데이터: -
- 상세 동작: 로그인 성공 시 만료시간이 포함된 access/refresh 토큰 쌍을 생성한다.
- 조건/권한: refresh 토큰 원문은 저장하지 않고 hash와 revoke 상태만 저장한다.
- 실패/예외: 토큰 생성 실패 시 세션을 만들지 않고 500/인증 오류를 기록한다.
- 검증 기준: 응답에 토큰 만료정보가 포함되고 DB에는 원문 refresh가 없다.

### FR-AUTH-08 토큰 갱신

- 우선순위: `P0`
- 요구사항: refresh 토큰으로 토큰을 재발급한다
- 인수 기준: 유효 refresh 시 신규 쌍 발급 / 폐기분 거부
- 관련 모듈/데이터: /auth/refresh
- 상세 동작: 유효한 refresh 토큰을 검증해 새 토큰 쌍을 발급한다.
- 조건/권한: 토큰 hash, 만료, revoke 상태를 모두 확인한다.
- 실패/예외: 만료, 폐기, 위조 토큰은 401로 처리한다.
- 검증 기준: 유효 토큰은 재발급되고 폐기 토큰 재사용은 차단된다.

### FR-AUTH-09 로그아웃

- 우선순위: `P0`
- 요구사항: 로그아웃 시 현재 세션을 폐기한다
- 인수 기준: refresh 세션 revoke 처리
- 관련 모듈/데이터: /auth/logout
- 상세 동작: 현재 refresh 세션을 revoke 처리하고 클라이언트 토큰을 폐기한다.
- 조건/권한: 로그인 사용자의 현재 세션에 한해 수행한다.
- 실패/예외: 이미 폐기된 세션은 멱등 처리하거나 204로 처리한다.
- 검증 기준: 로그아웃 후 동일 refresh 토큰으로 재발급할 수 없다.

### FR-AUTH-10 세션 유지/자동로그인

- 우선순위: `P1`
- 요구사항: 유효 세션이면 재방문 시 로그인을 유지한다
- 인수 기준: 유효 토큰 시 로그인 유지
- 관련 모듈/데이터: sessionStorage
- 상세 동작: 앱 재방문 시 저장된 세션을 확인해 로그인 상태를 복원한다.
- 조건/권한: access 만료 시 refresh가 유효한 경우에만 재발급한다.
- 실패/예외: refresh 만료/폐기 시 로그인 화면으로 이동한다.
- 검증 기준: 유효 세션은 유지되고 무효 세션은 자동 로그아웃된다.

### FR-AUTH-11 비밀번호 재설정

- 우선순위: `P1`
- 요구사항: 비밀번호 찾기/재설정을 지원한다
- 인수 기준: 이메일 인증 후 재설정
- 관련 모듈/데이터: -
- 상세 동작: 비밀번호 재설정 요청을 받고 이메일 인증 절차 후 새 비밀번호를 저장한다.
- 조건/권한: 토큰은 1회성, 제한 시간, 계정 소유자 검증이 필요하다.
- 실패/예외: 만료/사용된 토큰, 미가입 이메일은 안전한 응답으로 처리한다.
- 검증 기준: 유효 토큰으로만 재설정되고 기존 세션 처리 정책이 적용된다.

### FR-AUTH-12 비밀번호 변경

- 우선순위: `P2`
- 요구사항: 로그인 상태에서 비밀번호를 변경한다
- 인수 기준: 기존 비밀번호 확인 후 변경
- 관련 모듈/데이터: -
- 상세 동작: 로그인 사용자가 기존 비밀번호 확인 후 새 비밀번호로 변경한다.
- 조건/권한: 소셜 전용 계정의 변경 가능 여부를 별도 정책으로 정한다.
- 실패/예외: 기존 비밀번호 불일치, 정책 미충족은 400/401로 처리한다.
- 검증 기준: 변경 후 새 비밀번호로 로그인되고 기존 정책 위반 값은 저장되지 않는다.

### FR-AUTH-13 프로필 관리

- 우선순위: `P1`
- 요구사항: 프로필(이름/사진)을 조회·수정한다
- 인수 기준: 변경 저장 및 즉시 반영
- 관련 모듈/데이터: User, /me
- 상세 동작: 사용자 이름과 프로필 이미지를 조회하고 수정한다.
- 조건/권한: 본인 프로필만 수정 가능하며 이미지 형식/크기를 제한한다.
- 실패/예외: 권한 없는 수정, 허용되지 않는 파일은 거부한다.
- 검증 기준: 수정 저장 후 /me와 화면 표시가 동일하게 반영된다.

### FR-AUTH-14 라우트 보호

- 우선순위: `P0`
- 요구사항: 랜딩(/) 외 화면은 로그인 사용자만 접근한다
- 인수 기준: 비로그인 접근 시 로그인 리다이렉트
- 관련 모듈/데이터: -
- 상세 동작: 보호 대상 라우트 접근 전 인증 상태를 확인한다.
- 조건/권한: 랜딩과 공개 경로를 제외한 화면에 적용한다.
- 실패/예외: 비로그인 접근은 로그인으로 이동하고 원래 경로를 보존한다.
- 검증 기준: 비로그인 사용자가 보호 화면을 직접 열 수 없다.

### FR-AUTH-15 역할 기반 인가(RBAC)

- 우선순위: `P0`
- 요구사항: 역할에 따라 기능 접근을 통제한다
- 인수 기준: 권한 없는 작업은 403
- 관련 모듈/데이터: -
- 상세 동작: 역할별 권한을 서버 API와 화면 액션 양쪽에 적용한다.
- 조건/권한: OWNER/ADMIN/MEMBER 권한 매트릭스가 기준이 된다.
- 실패/예외: 권한 없는 요청은 UI 숨김과 별개로 API에서 403 처리한다.
- 검증 기준: 권한 없는 사용자가 직접 API 호출해도 작업이 실행되지 않는다.

### FR-AUTH-16 인증 만료 처리

- 우선순위: `P1`
- 요구사항: 토큰 만료 시 재발급 흐름을 처리한다
- 인수 기준: 401 시 refresh 후 재시도
- 관련 모듈/데이터: -
- 상세 동작: access 만료 응답을 감지해 refresh 후 원 요청을 재시도한다.
- 조건/권한: 재시도는 1회로 제한하고 동시 refresh 중복을 방지한다.
- 실패/예외: refresh 실패 시 세션을 정리하고 로그인 화면으로 이동한다.
- 검증 기준: 만료 상황에서 정상 재발급 또는 안전한 로그아웃이 동작한다.

### FR-AUTH-17 계정 탈퇴

- 우선순위: `P2`
- 요구사항: 사용자가 계정을 탈퇴할 수 있다
- 인수 기준: 탈퇴 시 데이터 처리정책 적용
- 관련 모듈/데이터: -
- 상세 동작: 계정 탈퇴 요청 시 사용자 상태와 관련 데이터 처리 정책을 적용한다.
- 조건/권한: 본인 인증 또는 재로그인 확인 후 실행한다.
- 실패/예외: 소유 프로젝트가 있거나 보존 의무 데이터가 있으면 정책에 따라 제한/대체한다.
- 검증 기준: 탈퇴 후 로그인 불가하며 데이터 처리 결과가 정책과 일치한다.

## ② 메인 대시보드 — 프로젝트 / 캘린더

### FR-DASH-01 프로젝트 생성

- 우선순위: `P0`
- 요구사항: 새 프로젝트(Space)를 생성한다
- 인수 기준: 명칭 입력 시 생성 / 생성자=owner
- 관련 모듈/데이터: Space
- 상세 동작: 프로젝트 명칭과 선택 정보를 받아 Space를 생성하고 생성자를 owner로 등록한다.
- 조건/권한: 로그인 사용자만 생성 가능하며 명칭 필수/길이 제한을 적용한다.
- 실패/예외: 필수값 누락, 중복 정책 위반, 권한 없음은 거부한다.
- 검증 기준: 생성 후 목록에 표시되고 SpaceMember owner가 생성된다.

### FR-DASH-02 프로젝트 목록 조회

- 우선순위: `P0`
- 요구사항: 참여 중인 프로젝트를 조회한다
- 인수 기준: 소속 프로젝트만 표시
- 관련 모듈/데이터: SpaceMember
- 상세 동작: 사용자가 멤버로 속한 프로젝트 목록만 조회한다.
- 조건/권한: SpaceMember 기준으로 필터링하고 삭제/비활성 프로젝트는 제외한다.
- 실패/예외: 권한 없는 프로젝트 ID를 직접 요청해도 노출하지 않는다.
- 검증 기준: 사용자별로 소속 프로젝트만 반환된다.

### FR-DASH-03 프로젝트 개요

- 우선순위: `P0`
- 요구사항: 회의목록·최근문서·Action Item·AI 진입점을 본다

### FR-MREG-02 참가 신청 승인

- 우선순위: `P0`

- 인수 기준: 신청은 승인 전 `PENDING`이며 HOST 승인 후에만 회의 접근권이 생긴다
- 관련 모듈/데이터: MeetingJoinRequest, MeetingParticipant
- 상세 동작: 인증 사용자가 회의 URL 또는 참가 코드를 입력해 신청하고, active HOST가 승인하면 `VIEWER` MeetingParticipant를 생성한다. Space OWNER/ADMIN은 회의 ACL 관리 override로 승인할 수 있다.
- 조건/권한: 신청자는 SpaceMember일 필요가 없다. 승인/거절은 active HOST 또는 Space OWNER/ADMIN만 실행한다.
- 실패/예외: 잘못된 코드, 중복 pending 신청, 이미 접근권이 있는 사용자, 권한 없는 검토, 처리 완료 신청의 재처리는 거부한다.
- 검증 기준: 승인 전에는 회의 접근이 차단되고, 승인 후에는 해당 회의만 접근 가능하며 SpaceMember 또는 프로젝트 접근권은 생성되지 않는다.
